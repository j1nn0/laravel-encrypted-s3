# ADR 0007: Treat SDK plaintext temp-file spill as an operator concern

The package exists to keep plaintext out of S3, but the AWS SDK can materialise that plaintext in a local temporary file. This was established by reading the installed vendor source and by direct experiments on PHP 8.2.33/Linux.

Guzzle's `Utils::streamFor()` opens `php://temp` with `r+` and no max-memory parameter at `vendor/guzzlehttp/psr7/src/Utils.php:551`. PHP keeps that stream in memory below 2 MiB, then spills it to a real file at 2 MiB (2,097,152 bytes) and above. The files are mode `0600` and are created in `sys_get_temp_dir()`. `stream_get_meta_data()` continues to report `php://temp` after the spill, so the existence of the file cannot be detected through the stream metadata.

The read path is affected after decryption: `Aws\Crypto\AesGcmDecryptingStream::createStream()` passes the decrypted plaintext string to `Psr7\Utils::streamFor()` at `vendor/aws/aws-sdk-php/src/Crypto/AesGcmDecryptingStream.php:101`. Consequently, `get()`/`read()`, `readStream()`, and responses built through `response()`, `download()`, or `serve()` can create a local plaintext file for plaintext at or above the threshold. `readStream()` returns a detached resource, so the caller owns the close that causes the temporary file to be unlinked.

The string write path is affected as well: `S3EncryptionClientV3::putObjectAsync()` passes the string `Body` to `Psr7\Utils::streamFor()` at `vendor/aws/aws-sdk-php/src/S3/Crypto/S3EncryptionClientV3.php:253`. Therefore `put()`/`write()` can create a local plaintext file at or above the threshold before encryption. A `writeStream()` call with a caller-supplied resource takes Guzzle's resource branch and does not create an additional SDK plaintext copy; any spill in that case belongs to the caller's stream.

The temporary file is normally unlinked when its stream closes, but abnormal termination skips destructors. A `SIGKILL`, OOM kill, or segmentation fault can therefore leave the file behind with its plaintext contents intact. The directory is selected by `sys_get_temp_dir()`: the `sys_temp_dir` ini setting when configured, otherwise `TMPDIR`, `TMP`, or `TEMP` captured at process start, and finally `/tmp`. A runtime `putenv()` change does not alter that cached value.

We deliberately do not steer string writes through `php://memory`. That could avoid the SDK-created spill on writes, but the read path has no equivalent application hook: the SDK creates its `php://temp` stream internally after decryption. Operators must therefore treat the temporary directory as plaintext-exposed regardless. `php://memory` also has no spill valve and would add roughly another full plaintext copy at peak memory for large writes, trading a known local-file exposure for a real memory-exhaustion risk without changing the required operator posture. There is no SDK or Guzzle option to replace this `php://temp` wrapper, and the `php://` stream wrapper cannot be replaced with `stream_wrapper_register()`.

The durable control is operational: configure `sys_temp_dir` in `php.ini`, or set `TMPDIR`/`TMP`/`TEMP` before the process starts, to a RAM-backed `tmpfs` or an encrypted volume. This ADR records the limitation rather than adding a write-only mitigation that would not change the package's overall security posture.
